Configuration engine

Every serving change the panel makes — vhosts, PHP pools — has been versioned since the first apply. The configuration engine is the part you can see: the version timeline on each site, one-click rollback, and drift detection that reports what it finds and never silently "fixes" it.

The timeline live in the panel

Open a site in Sites and scroll to Config history & drift. Each applied configuration is a version: who rendered it, when, and its exact size. History is append-only — nothing is ever edited or deleted, including PHP pool files, which are versioned the same way vhosts are.

Rollback that writes forward live in the panel

Rolling back to an old version does not rewind history — it re-applies that version's stored bytes as a new version through the same health-gated pipeline as any other change (staging write → atomic swap → health check → auto-rollback). The whole operation is recorded as a transaction: pending while the apply runs, then applied or failed with the error. A failed rollback leaves the previous configuration serving — a transaction row exists for the attempt either way.

PHP pool rollback is an honest gap for now: the agent addresses pool files per PHP version, and the pool-target apply path lands with its own amendment. The API refuses with that exact explanation instead of pretending.

Drift: reported, never reconciled live in the panel

Check drift now hashes the file on the node against the active version's bytes. A mismatch creates a drift event — visible in the site's card, resolvable as reconciled, investigated or ignored once a human has decided what happened. The agent does not overwrite drifted files on its own; that is the constitutional rule (§P.7): the panel reports, the admin chooses.

A file that vanished from the node is drift too (exists: false) — the classic "I cleaned up /etc/nginx/conf.d by hand" incident becomes a visible event instead of a mystery outage at the next reload.

The apply pipeline, everywhere

Everything that lands on the node goes through the same primitive: staging write, atomic rename, health gate, byte-for-byte rollback on failure. vhosts, pool files and certificates share it; the timeline, the transactions and the drift checks are the audit surface on top.

What is not live yet

  • Periodic drift checks — drift runs on demand today; the 15-minute scheduled sweep arrives with the scheduler infrastructure (the on-demand path and the event ledger are the same either way).
  • Pool-target drift and rollback — see the callout above.
  • config.render as an agent command — deliberately absent: rendering is deterministic and panel-owned; a second renderer would be two sources of truth for the same bytes.
