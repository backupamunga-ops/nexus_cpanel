Files & trash

The browser file manager runs on top of the agent's confined filesystem commands. The control plane decides whether (permissions, ownership, audit); the agent decides where (path confinement on the node). Between the two, a file operation has no single point of failure and no single point of deception.

Browsing and editing live in the panel

Open Files, pick a hosting account, and navigate from the account home. You can create directories, upload files (10 MiB per file), download them (base64-wrapped, with an explicit flag when the 10 MiB read cap truncated the file — a silent partial download would be worse than an error), and change permission bits.

Paths are anchored at the account home: relative paths resolve under it, absolute paths must already be inside it, and .. is rejected before it ever reaches a signed command. The agent re-checks everything with symlink-aware confinement — a planted symlink cannot redirect a panel operation outside the account.

Trash with a 30-day retention live in the panel

Deleting a file or directory moves it to the account's trash (.nexus-trash/ on the node, with a timestamp prefix) and records a ledger row with a purge_after deadline 30 days out. From the trash panel you can restore an entry (the file moves back) or purge it immediately.

The Purge expired entries action runs the agent's purge for the account. Reconciliation is honest by construction: the agent reports exactly which files it removed, and only those entries leave the ledger — a file the agent could not remove stays in the trash and in the ledger, visible instead of vanishing.

SSH keys live in the panel

Import per-account public keys (ed25519, RSA, ECDSA — single-line OpenSSH format). The panel computes the SHA-256 fingerprint at import and refuses duplicates, so a mis-pasted key is caught at import, not at 2 a.m. when it "doesn't work".

Deploy to node writes the imported keys to the account's ~/.ssh/authorized_keys through the agent's ssh.deploy_keys (ADR-0010). The reconcile is marker-based: every line the panel owns ends with a nexus-managed:<fingerprint> comment, and only those lines are rewritten — keys added by hand on the node are preserved verbatim. The per-key on node badge is read live from the node's actual file on every view; nothing is cached in the database, so the badge cannot lie (D-11).

  • ~/.ssh is 0700 and authorized_keys is 0600, both owned by the account user.
  • Removing a key in the panel removes it from the node on the next deploy — the UI says so at removal time.
  • Hand-copied panel lines (marker included) become panel-managed by definition — the marker means "the panel owns this line".

What the agent refuses

  • Paths outside the account home, including symlink redirection.
  • Deleting the account home or the trash root itself.
  • Content above the 10 MiB cap (upload and download alike).
  • Overwriting an existing file unless the operation says so explicitly.
  • Special permission bits (setuid/setgid/sticky) on chmod — panel chmod is for web files, not privilege games.

FTP accounts live in the panel

Each hosting account can have vsftpd virtual users (per API spec §4.12, agent amendment ADR-0011). A login is globally unique, chrooted to a directory inside the account's home, and optionally read-only. The panel stores only the registry; the password is hashed on the node (SHA-512-crypt, fresh salt per write via openssl passwd -6) into the pam_userdb and never persisted anywhere else.

Node prerequisites: vsftpd must be configured once per node with pam_userdb pointing at the panel's user DB and user_config_dir at the panel's per-user directory (a runbook task — the installer milestone automates it). Accounts provision fine before that but cannot authenticate; nodes without db_load report the skipped userdb rebuild explicitly in the API response instead of pretending the login works.
