Sites & domains

A site is a domain served from a hosting account. This chapter covers what is live in the panel today: creating sites, subdomains, aliases and redirects — and the provisioning pipeline that stands behind every serving change: staging write → atomic swap → health check → auto-rollback, with a versioned history of every applied configuration.

Creating a site live in the panel

Open Sites in the sidebar and use the New site form: an FQDN (example.com), the hosting account the site belongs to, a type (primary, addon or parked) and — optionally — the PHP version the site will use. On submit the panel does, in order:

  1. validates the FQDN strictly (lowercase, RFC host labels, 1–253 chars) and checks the account is active;
  2. tells the agent to create the document root inside the account's home (/home/<user>/domains/<name>/public_html by default), confined by the agent's path policy — the panel cannot ask for paths outside the home, and the agent would refuse even if it tried;
  3. renders the nginx vhost from panel-owned templates and applies it atomically (see The apply pipeline below);
  4. only then writes the database row, the first configuration version and the audit entry — all in one transaction.

The order is deliberate: the agent owns the machine, the database describes it. A failed agent call leaves no row — the panel never records a site it could not actually provision. The error you see in the UI is the one the agent returned.

Who can see and manage sites

Sites belong to hosting accounts, and the ownership boundary follows the account: server admins see every site; everyone else sees only sites of accounts they hold an active access row for. A site outside your visibility answers 404, not 403 — account and site existence cannot be probed across the boundary (API spec §3.2). Within an account:

Subdomains, aliases, redirects

All three live on the site's detail panel (select a site in the list).

  • Subdomains are separate sites under the domain (blog.example.com) with their own document root and their own vhost file. One DNS label at a time; duplicates are refused with 409.
  • Aliases are additional names that serve the same site. Adding or removing an alias rewrites the parent's vhost server_name list and re-applies it.
  • Redirects map a path to an http(s) destination with status 301, 302, 307 or 308. Exact-match by default, or wildcard (prefix) matches. Redirect changes also re-apply the parent's vhost.
Redirect paths and destinations are embedded in nginx configuration, so they are validated against a strict allowlist (URL-safe characters only — no whitespace, quotes, braces or semicolons). Anything that could form an nginx directive is rejected with 422, not escaped.

The apply pipeline

Every vhost change goes through the same pipeline on the node:

  1. Staging write — the new configuration lands in the target directory under a staging name;
  2. Atomic swap — an atomic rename puts it in place; readers never see a half-written file;
  3. Health check — the agent runs the webserver's config test. On nodes without a webserver binary (development), the result is reported as skipped with the reason — never silently ignored;
  4. Auto-rollback — if the health check fails, the previous configuration is restored byte-for-byte and the change is rejected with the test output.

Configuration history

Each successful vhost apply records a new configuration version for the site (who rendered it, when, the exact bytes). History is append-only; deactivating a site marks its versions inactive without deleting them. The configuration engine (version timeline, drift detection, one-click rollback) builds directly on this history and ships with the config-engine milestone.

Site logs live in the panel

Every vhost the panel renders now emits per-domain access_log and error_log directives pointing into the account's own home — /home/<user>/logs/<domain>.access.log and .error.log. The site detail screen has a Logs card that tails either log (100–1000 lines) through the agent's confined file-read path, so the viewer inherits the same 10 MiB cap and path confinement as the file manager.

  • A missing log file is shown honestly as “no log yet” — the file appears after the first request following a vhost apply.
  • Sites created before per-site logging receive their log directives on the next vhost re-apply — any site edit triggers one.
  • Log rotation is not configured yet (a runbook item until the logrotate milestone).

What is not live yet

  • FTP accounts — deferred until the ftp.* agent category lands (see the files chapter for what the file manager covers today).
  • Staging clones and git deployments — later phases (P6).
