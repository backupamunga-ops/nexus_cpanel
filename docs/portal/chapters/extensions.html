Extensions & SDK

Extensions are add-ons that run outside the panel as their own little service and talk to it over a signed, versioned protocol. They can add dashboard cards, react to things that happen (a backup finishing, a backup failing), and call a small, carefully-fenced slice of the panel API. What they can never do is touch anything you did not approve — nothing is granted until you review and allow it, and every call they make is written into the tamper-evident audit log.

The idea in one minute

An extension is a small web service that publishes a manifest — a JSON file saying who it is, what it wants to see, and where the panel can reach it. You install it by pasting its manifest URL on the Extensions screen. The panel fetches the manifest, checks it against a closed list of allowed permissions, and parks the extension in disabled state with nothing granted. You then see exactly what it is asking for and either Approve or Reject. Approval hands you a secret exactly once — paste it into the extension and it starts working. Lose it? Uninstall and install again.

What extensions can ask for

Permissions are a closed list — extensions cannot invent new ones. The read scopes cover accounts, sites, mail, DNS, databases, SSL, backups, the audit log and users. The notification:write scope lets an extension post a message into your notification center. The write scopes (sites, mail, DNS, backups) are declared but refused in v1.0 — every extension write would need your personal per-call confirmation, and that confirmation queue arrives in a later release. Until then, a refused write notifies you and changes nothing.

How the panel talks to an extension

Every call the panel makes to an extension carries three headers — an extension id, a timestamp, and a signature computed from the shared secret over exactly what is being sent. The extension must check the signature and refuse anything older than 60 seconds. Extensions call the panel through /api/v1/ext/* only — a separate, rate-limited (60 calls/minute) doorway where every request is checked against the scopes you granted and audited under the extension's own name. The main panel API is unreachable from an extension, full stop.

Health and honesty

The panel pings every enabled extension once a minute. One that stops answering is marked errored, its doorway is closed, and you get a notification — the same happens again in reverse when it comes back. Widget cards on the dashboard are plain sandboxed iframes: they get the color theme, and nothing else.

The example extension

nexus-example-reporter ships in the repository (examples/) — a couple hundred lines of dependency-free Node.js that posts a backup summary to a webhook of your choice and shows a “Last backup” card on the dashboard. It verifies every panel signature the way a production extension should, and it is the acceptance test for the whole SDK: if it runs unmodified against a fresh install, the SDK works.

Not yet (honest list)

  • Per-call confirmation queue for the write scopes (v1.x trust levels).
  • PostgreSQL storage namespaces for extensions that ask for them (spec §8) — provisioned during the live-VM acceptance run.
  • Marketplace (spec §10) — v1.0 installs by manifest URL only.
