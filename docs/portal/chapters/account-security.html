Your account security

Second-factor authentication, device sessions, and scoped API tokens — the security controls that protect your login rather than your hosting accounts. Everything on this page is enforced server-side and hash-chained into the audit log.

Sessions & devices live in the panel

Every sign-in creates its own session with a 7-day rotating refresh secret, bound to your browser's device fingerprint and stored only as a SHA-256 hash. Open Sessions in the sidebar to see every live session: which browser, which IP, when it was last used. The session you are using right now is marked this device.

  • Revoke a device — its refresh secret dies immediately; the next access-token expiry (≤ 15 minutes) ends its access.
  • Sign out on the current device revokes that session.
  • Reuse detection — a refresh token that was already rotated and comes back is treated as theft: every session of your user is revoked and the event is audited as auth.session.reuse_detected.
The panel's refresh secret lives in an httpOnly, SameSite=Strict cookie scoped to the auth endpoints. Page scripts can neither read nor exfiltrate it; cross-site requests never carry it. This closes the token-theft path that localStorage-based panels have.

Two-factor authentication live in the panel

NexusPanel supports TOTP (RFC 6238, the same standard as Google Authenticator, Aegis or 1Password) plus ten one-time backup codes. Enable it under Security in the sidebar: scan the QR code (or paste the secret), confirm one live code, and save the ten backup codes — shown exactly once. When 2FA is on, the sign-in form asks for a 6-digit code after your password; a backup code works in the same field and is burned on use. A wrong second factor counts as a failed login attempt — five in a row lock the account for 15 minutes, so the lockout protects the second factor too.

The same screen regenerates backup codes and disables 2FA — both require your password. Management routes are also available over the API for headless setup: 

POST /api/v1/auth/2fa/setup          → secret + otpauth:// URI (scan into your app)
POST /api/v1/auth/2fa/verify         {"code": "123456"}   → enables 2FA, returns 10 backup codes
GET  /api/v1/auth/2fa/backup-codes   header X-Confirm-Password: …  → regenerate (old ones burn)
POST /api/v1/auth/2fa/disable        {"password": "…"}

Secrets at rest are AES-256-GCM encrypted with a key that lives outside the database (CP_SECRETS_KEY); a database dump alone reveals neither TOTP secrets nor backup codes. Backup codes are Argon2id-hashed on top.

API tokens live in the panel

Automation credentials for CI, scripts and the future SDK/CLI, managed on the API tokens screen. A token is an opaque npt_… secret that is shown exactly once and stored only as a SHA-256 hash. A token can do nothing more than its scopes, and never more than its owner could do interactively — even its owner's admin rights do not leak through. Rotation re-mints the secret without extending the original expiry; credential management itself (create/rotate/revoke) is session-only: a stolen automation token cannot mint new credentials or disable your 2FA. 

POST   /api/v1/tokens            {"name","scopes":["account:list","audit:read"],"expires_at":…}
POST   /api/v1/tokens/{id}/rotate                    → new secret, original expiry kept
DELETE /api/v1/tokens/{id}                           → revoke (idempotent)

Send it as Authorization: Bearer npt_…. Unknown or revoked secrets, expired tokens, and tokens from disabled owners all fail with the same uniform 401 — no oracle — while rejected-but-known tokens are audited as api_token.auth_rejected.
