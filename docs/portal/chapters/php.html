PHP per site

Each site runs its own PHP-FPM pool: an isolated process group with its own socket, its own limits, and its own PHP version. One site's memory spike cannot starve its neighbors — that is the point of per-site pools.

Choosing a version and pool settings live in the panel

Open the site in Sites and use the PHP card. The version selector offers PHP 8.1–8.4; versions not in the account's package are marked and rejected server-side, and versions not installed on the node are refused by the agent with a clear precondition — installing PHP versions is an operator task, never a signed-command away.

Pool settings the panel can manage (unknown keys are rejected on both the control plane and the agent — a typo must never silently enforce nothing):

  • pm — dynamic, static or ondemand process management;
  • pm.max_children and the spare-server pair — the process budget (1–500);
  • memory_limit, upload_max_filesize — sizes like 128M;
  • max_execution_time — 1–300 seconds.

What lands on the node

A pool file at /etc/php/<version>/pools/<domain>.conf — the site's user and group, a dedicated socket (/run/php/php<version>-fpm-<domain>.sock), and the settings above as php_admin_value entries. The rendered file is recorded verbatim in the site's configuration history, so the config engine treats PHP pools and nginx vhosts alike: versioned, audited, comparable for drift.

Changing and removing

  • Same version, new settings — the pool file is rewritten in place.
  • New version — the old pool file is removed, the new one created; the site's php_version and the config history update together in one transaction.
  • Remove — the pool file is deleted and the site runs without PHP until a version is chosen again.
