Backups & restore

Every backup is an artifact: a gzipped tar of the account home, the site subtree or a database dump, plus a JSON manifest carrying its checksum. Artifacts can be encrypted with age before they leave the node (security control C15) and can land on a local directory, an S3-compatible bucket or an SFTP server. The restore flow always shows you what is inside an artifact before it touches anything.

Destinations live in the panel

Open Backups and add a destination: local (a directory under the agent's backup root), S3-compatible (any bucket speaking the S3 API — uploads run through rclone), or SFTP (batch-mode OpenSSH client with a pinned host key when you provide one). Press Test to prove the destination with a real round trip (upload → download → checksum → clean up) before pointing jobs at it.

The config you type — bucket keys, the SFTP private key — is stored as an AES-256-GCM envelope (SecretBox, ADR-0009). The panel never shows it back: it is decrypted only at the moment an agent call needs it, and the audit trail carries a fingerprint, never the material. Secrets ride to the node through the signed command channel once and live in the child process environment or a 0600 temp key file — never in argv, logs, or the agent's write-ahead log.

Encryption (C15) age, master-key protected

  • Destination config accepts age recipients (public keys). Any destination with recipients produces .tar.gz.age artifacts — encrypted on the node, before upload.
  • Decrypting requires the age identity file (the master key) configured on the node performing the restore. It is a node-local file — it never crosses the API or the command channel.
  • The negative path is part of the design: an encrypted artifact on a node without its identity fails loudly — restore and verify report a precondition error, they never silently skip encryption. A wrong master key fails the same way.
  • A destination without recipients stores plaintext artifacts; runs carried on it are flagged honestly in the UI and docs.

Jobs & schedules live schedules fire with B13

A job binds a scope to a destination: a whole account home, a site subtree, a MariaDB database (the agent dumps it first, ADR-0001 engines only in v1.0), or the agent's own managed server config. Every job carries a retention policy — grandfather-father-son: N daily, N weekly and N monthly restore points survive outside the plain retention_days window.

The cron schedule is stored and validated, but the engine that fires schedules lands with the job framework (B13) — the badge on every job says so, and Run now is the live path today. Stated, not hidden.

Runs: the honest journal live

Every attempt becomes a run row before the agent is called, and it tells the truth about what happened: running → success or failed (with the agent's error message verbatim). A successful run records the artifact name, its size and the SHA-256 over the final (post-encryption) bytes.

The verified badge is earned, never inferred. It appears only after a real proof:

  • Verify — re-hashes the artifact at the destination against the recorded checksum and, for encrypted artifacts, actually decrypts it with the node's master key. Bit-rot and key loss both fail here.
  • Test-restore (dry-run restore) — fetches, decrypts, checksums and extracts the whole artifact into a scratch area. Nothing is written back.

A plain successful backup shows amber success — not verified yet until one of those proofs runs.

Restore <- with preview live

Preview lists the manifest and the sanitized entry listing (first page) before anything is extracted — including whether the checksum matches the manifest. Restore then behaves by scope: account/site artifacts are extracted inside the owning account's home (never over system paths — C13 confinement); a database artifact's dump is additionally re-imported into the database through the same confined path the dump tool uses. Restore refuses artifacts whose bytes do not match their manifest checksum, and skips symlinks, devices and path escapes with a count instead of following them.

Retention live

After every successful run the panel applies the job's GFS policy over its run registry: everything inside retention_days stays, plus the newest N daily / N weekly (Mondays) / N monthly (1st) restore points; the rest is purged at the destination. As a second seatbelt, the agent protects any artifact whose own manifest claims a newer date than the purge cutoff — the registry decides, the manifest vetoes.

Not yet (honest list)

  • Schedule firing — the cron engine is the job framework (B13); today schedules are stored and Run now is the live path.
  • Account-holder self-service restore ("my backups") — backups are admin-managed in B10; the account-holder guide lands later.
  • SFTP purge — retention currently purges local and S3 (rclone) destinations; SFTP-destination purge is planned.
  • Age identity provisioning UX — the master key file is provisioned by the installer today; a rotation flow follows the master-key rotation runbook work.
  • Full-node bare-metal restore — v1.0 restores per-scope artifacts; a whole-node rebuild path is future work.
