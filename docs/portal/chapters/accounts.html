Accounts & packages

Hosting accounts are the tenants of a node. Packages define what an account may consume. This page covers what works today (M0) and what lands with the identity phase (P2).

live in M0

Accounts today

  • List & inspect — every account with status, UID and home directory.
  • Create — see Your first hosting account for the full flow including what the agent does on the node.
  • Suspend / resume / delete — each action maps to a typed agent command and is hash-chained in the audit log.
  • Live usage — CPU time, memory and process count sampled from the account's cgroup slice and pushed over WebSocket. Disk usage joins when the filesystem category lands (P3).
live in P2

Packages & quota enforcement

Packages are real now. Server admins manage them on the Packages screen (or /api/v1/packages); every account is created on a package, and per-account quota overrides can adjust the merged set at any time.

  • Fail-closed quota keys — cpu (0.1-core granularity, ≤ 64), mem_mb (≤ 1 TiB), disk_mb (≤ 10 TiB), inodes, processes (≤ 4096). Unknown keys are REJECTED at creation — a typo'd key would silently enforce nothing.
  • Real agent enforcement — quotas reach the node as cgroup v2 limits via account.quota / account.modify (both commands are fully implemented now — no more stubs).
  • Honest override semantics — PATCH /accounts/{id} with {"quotas": …} sends the MERGED set (package ← override) to the agent, persists only the override partial, and the audit entry records applied AND skipped keys. The disk/inodes enforcement gap is explicit, never silent.
  • Soft deletes — a package referenced by live accounts cannot be deleted (409 with the count); history is retained.

Access sharing (delegation)

An account can be administered by more than one panel user — without sharing anyone's login. Sharing manages the exact user_hosting_account_access rows the permission guard enforces on every account route, so a granted role takes effect immediately and everywhere (list, read, suspend, quotas, usage).

  • Roles — owner (full control, exactly one per account, cannot be granted or revoked through the sharing API — ownership transfer is a separate, future flow), admin (everything except deletion and except ownership), member and readonly (view only). The role → permission matrix lives in one place in the control plane and is unit-tested.
  • Who may delegate — the owner, admins, and server admins, via the account:share permission. Members and readonly users can never pull in more people (no transitive trust escalation).
  • Grant — POST /accounts/{id}/shares with {"email": …, "role": …}. Fail-closed validation: the user must exist and be active (unknown, deactivated and deleted users all get the SAME 404 — no existence oracle), duplicate active grants get 409 (revoke first, then re-grant to change a role), and the owner role is rejected outright. Your identity is recorded as the grantor.
  • Revoke — DELETE /accounts/{id}/shares/{shareId} soft-revokes the row (history kept; a fresh grant creates a NEW row). Misses are a uniform 404 whether the id is unknown, already revoked, or belongs to a different account.
  • Audited — account.share.grant and account.share.revoke are hash-chained into the audit log in the same transaction as the row write.
  • In the UI — every account card has a Sharing panel: the active rows, who granted them, and the grant form (shown only when your role may delegate).

Permission model

Every accounts endpoint declares the permission it requires (account:list, account:create, account:suspend, account:resume, account:delete, account:read, account:share) and the server enforces it on every request — the UI hides what your role cannot do, but the API is the real boundary. Account-scoped permissions resolve from your role in the account's access rows; account:list admits every authenticated user but the service narrows rows to your grants.
