Server settings

Server settings are the admin-editable, platform-wide configuration values — instance naming, security policy numbers, audit retention. They live in a single system_settings table backed by a whitelist: the control plane owns a catalog of typed definitions, and nothing outside that catalog can exist. This chapter covers what is live today and how the values relate to the runtime.

The whitelist is the safety model live in the panel

Open Server settings in the sidebar (server admins only). The form is generated from what the server reports — type, bounds, default and current value for each key — so the UI can never offer an input the API would reject. There is no free-form key field: unknown keys are refused on read with 404 and on write with 400, so a typo'd key can never silently enforce nothing. Values are validated fail-closed (booleans are strict, integers carry explicit minimums and maximums, strings are trimmed and length-bounded) and a rejected save shows the exact rule that was broken.

  • Non-secret by definition — only configuration lives here. Secrets (JWT key, TOTP envelope key, SMTP credentials) stay in env/secret files, outside the database.
  • Every change is audited as settings.update in the tamper-evident chain — with the acting admin, the previous value and the new value, written in the same transaction as the row itself. A config change without its audit entry is impossible.

Stored vs enforced — an honest distinction D-11

Each setting carries an explicit enforcement badge in the UI. Values marked enforced are read by the running system today: the four security integers — lockout threshold, lockout duration, session lifetime and the password minimum — are read live from this table at every enforcement event (each login attempt, each lock applied, each login and refresh rotation, every password set). There is no cache and no restart: an admin's change takes effect on the very next event. If a read fails, the seam falls back to the catalog default — a degraded read can only ever return the shipped baseline, never something weaker. Values still marked stored — not yet enforced are validated and audited but their runtime seam (instance-name headings, the sign-in banner, a mandatory-2FA gate, audit-log pruning) has not landed yet. Deliberately, the panel never pretends a stored number is already protecting anyone.

Decision D-11 (master documentation §10): server settings are store-first — validated, audited values now; enforcement seams wired incrementally, each with its own tests. With the four security integers wired, the former environment variables (LOCKOUT_THRESHOLD, LOCKOUT_MINUTES, REFRESH_TTL_DAYS) and the code-fixed 12-character minimum are retired: this table is the single source of truth for them, and the access-token TTL (15 min, C3) remains deliberately env-fixed.

Current catalog live

  • platform.instance_name — display name (1–64 chars; not yet enforced).
  • platform.login_notice — optional sign-in banner text (≤ 200 chars; not yet enforced).
  • security.totp_required — require 2FA for all users (not yet enforced).
  • security.max_failed_logins — lockout threshold, 3–10 (default 5; enforced).
  • security.lockout_minutes — lockout duration, 5–1440 (default 15; enforced).
  • security.password_min_length — 8–128 (default 12; enforced — backup codes are hashed outside this policy).
  • security.session_ttl_days — refresh-token lifetime, 1–30 (default 7; enforced — cookie Max-Age follows).
  • audit.retention_days — audit-trail retention, 30–3650 (default 365; pruning not built).

API surface live

GET    /api/v1/settings               settings:read     (catalog with effective values)
GET    /api/v1/settings/{key}         settings:read     (404 on unknown key)
PUT    /api/v1/settings/{key}         settings:write    (400 on unknown key / bad value)

settings:read / settings:write are part of the permission vocabulary (C6) and can be granted to scoped API tokens (C4) for automation. Writes are audited as settings.update with from → to.
