Resellers

A reseller is a hosting account that has been granted reseller capability: it can be branded, it can sit inside a nesting hierarchy, and it can serve the panel from its own domain. This chapter covers what is live in the panel today — capability grants, the nesting policy, white-label branding and custom-domain registration — and how sessions stay isolated between branded origins (security control C14).

Granting reseller capability live in the panel

Open Resellers in the sidebar (server admins only). The grant form lists every hosting account that is not yet a reseller; pick one, optionally choose a parent reseller, and confirm. The reseller record hangs off the hosting account — the account keeps its OS identity, quota and agent provisioning, and the reseller layer adds the commercial surface on top. Removing a reseller later is a soft delete: the audit history stays, the hosting account is untouched.

  • One reseller per account — a second grant on the same account is refused with 409.
  • Every grant is audited as reseller.create in the tamper-evident chain, including who granted it, the parent and the resulting depth.

Nesting & the depth policy live in the panel

The data model supports unlimited nesting; the policy caps it. By default a reseller tree may be 2 levels deep (a reseller and one tier of sub-resellers). Server admins can raise or lower the cap per installation with the RESELLER_MAX_DEPTH environment variable — there is no code ceiling, it is an admin-controlled policy knob (Decision 3 in the specification set).

  • Re-parenting — a reseller can be moved under another reseller (or up to the top level with a null parent). The whole moved subtree shifts with the node; a move that would push any descendant past the cap is refused with a 400 naming the account that would overflow.
  • No cycles — a reseller can never be re-parented under itself or one of its own descendants.
  • No orphans — deleting a reseller that still has live child resellers is refused with 409 until the children are re-parented or removed first.

White-label branding live in the panel

Each reseller carries a branding object rendered on the branded panel surface: brand_name, primary_color / accent_color (#rrggbb), an https://-only logo_url and a login_message. Validation is fail-closed — malformed values are rejected with a clear 400 rather than silently ignored — and updates are full replacements: send the complete object you want stored, exactly like package quotas.

Custom panel domains live in the panel ADR-0003

A reseller can serve the panel from panel.brandco.example instead of the provider's host. Registration in the panel sets the domain with status pending; the certificate issuance that flips it to active is an out-of-band ACME process on the node. Domains are validated strictly (hostnames only — no ports, paths or wildcards) and unique among live resellers: two resellers claiming one origin would defeat the isolation described below.

C14 — session isolation across branded origins

When a branded domain is active, sessions are pinned to the origin they were created on, in two cooperating layers:

  • Cookie layer — the refresh cookie carries no Domain attribute (host-only): the browser itself never ships reseller A's cookie to reseller B's site.
  • Server layer — every session records the Host it was minted on. On each refresh the request's Host is classified against the active reseller domains: crossing from one branded origin to another — or between a branded origin and the canonical panel — is refused with the refresh path's uniform 401, the session is revoked and the attempt is audited as auth.refresh with reason host_crossing.
Cross-origin replay (a copied token presented on the wrong host) is treated like a device-fingerprint mismatch: the session dies and re-authentication is required. Domains still pending do not participate in enforcement, so registering a domain never locks existing users out before it actually activates.

API surface live

GET    /api/v1/resellers                     reseller:list
GET    /api/v1/resellers/{id}                reseller:read
POST   /api/v1/resellers                     reseller:create
PATCH  /api/v1/resellers/{id}                reseller:update      (re-parent)
DELETE /api/v1/resellers/{id}                reseller:delete      (soft)
GET    /api/v1/resellers/{id}/branding       reseller:read
PATCH  /api/v1/resellers/{id}/branding       reseller:update      (full replace)
POST   /api/v1/resellers/{id}/custom-domain  reseller:update      (status: pending)
DELETE /api/v1/resellers/{id}/custom-domain  reseller:update

Audited operations: reseller.create, reseller.update, reseller.delete, reseller.branding.update, reseller.custom_domain.set, reseller.custom_domain.clear — all in the same hash-chained chain as every other privileged action.
